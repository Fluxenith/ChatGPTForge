# Portable records

## Handoff

Copy this structure, replacing placeholders with actual evidence. Keep secrets out; reference local receipts without embedding their tokens.

```text
Objective and accepted scope:
Deferred/excluded work:
Source release/HEAD and current fingerprint:
Task ID, current state, operation IDs and receipt locations:
Current owner and required handoff/claim step:
Completed results with exact evidence:
Failures and inspected post-state:
Runtime/transport/Host distinction:
Next independent action:
External prerequisites still needed:
Completion commands and expected outcome:
```

A prepared handoff is not a successful claim. Sending a message to another conversation still requires the user's applicable authorization. Follow live handoff contracts rather than pasting a write lease into a shared guide.

## Reusable lesson

```text
Trigger:
Observed failure (version/platform/context):
Root cause supported by evidence:
Smallest correction:
Verification and receipt:
Applicability limits / counterexample:
Sensitive details removed:
Review or expiry condition:
```

Use `plan_lesson` when available and appropriate, or a project-owned reviewed record. Distinguish a demonstrated correction from a hypothesis. Never turn one fixture into a universal claim. Onboarding, configuration and source changes invalidate evidence tied to older versions.

## Release closure

Record the final entrypoint, manifest hash, fixed acceptance results, task completion state, remaining coverage and deployment ownership. Check that docs and actual state agree. Release preparation does not authorize publication, sending messages or operating unrelated applications.
