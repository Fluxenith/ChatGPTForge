# Plans, handoffs, and reusable experience

Use a plan for sustained work, sized around independent reviewable outcomes. `plan_status` timing advice is a heuristic, not a platform deadline. Do not stop after every step when the user authorized a combined delivery.

`plan_update` done requires current passing evidence. Reopening a verified step invalidates the old acceptance. If using `plan_closure`, distinguish the recorded phase from an actual Git commit or submitted prompt: the phase itself performs neither action. HEAD/fingerprint changes after a committed closure require reopening and renewed validation.

Before a handoff, retain the actual task/plan state, source HEAD/fingerprint, accepted constraints, completed evidence, remaining gaps and required user actions. Follow the live handoff tool contract. A prepared message is not a submitted one; a submitted message is not a receiving claim. After ambiguous submission, inspect post-state instead of sending again. Do not open or message a different conversation without the user's applicable authorization.

Write reusable `plan_lesson` notes only from demonstrated evidence: the trigger, actual failing/successful result, narrow correction, applicability limits, and source/operation references. Do not convert a one-off failure into a universal restriction. Keep secrets, machine endpoints and personal paths out of portable guides. Machine-specific receipts remain in the state directory.

Portable review cases for this guide:

- An indexing response: continue the same read; do not claim symbols were returned.
- A Gateway write returns unknown: inspect its durable receipt and external effect; do not resend with a fresh ID.
- An installed browser exposes recording: run a bounded local fixture and verify recorded code/video before claiming acceptance.
- A source change after task verification: renew the affected acceptance before completion.
- Daily Chrome or second Tunnel excluded: keep those items pending without blocking unrelated work or changing their settings.

These cases are review scenarios, not claims of an independent model evaluation.
